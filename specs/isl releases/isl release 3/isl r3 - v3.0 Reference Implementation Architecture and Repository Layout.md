# Reference Implementation Architecture and Repository Layout
**Status:** Normative
**Release:** r3
**Depends On:** ISL v0.0, ISL v0.1, ISL v1.x, ISL v2.x
**Supersedes:** ISL r2 v3.0 The Reference Implementation Architecture, ISL r2 v3.1 The Reference Repository Layout and Service Topology

## 1.0 Scope

This document defines the Reference Implementation Architecture and the Reference Repository Layout for the ALETHEIA platform. It specifies the implementation-level components, module responsibilities, service boundaries, internal contracts, persistence boundaries, integration points, repository organization, build and test automation, service topology, and conformance requirements for a reference implementation of the platform architecture defined in ISL v2.0.

This document does not require a single programming language, framework, database, model provider, cloud provider, or deployment platform. It defines a technology-neutral reference architecture that implementations MAY realize using different stacks while preserving the required logical boundaries and behavioral contracts.

This document does not define the artifact repository layout for systems generated by ALETHEIA; that concern is defined in ISL v2.3. This document defines the repository that contains the platform implementation itself.

Shared conventions — normative language, field requirement levels, identifiers, shared enums, design principles, the common error model, the common telemetry model, and the conformance framework — are defined in ISL v0.1 and referenced here rather than redefined. The full telemetry event catalog is defined in ISL v2.3 and referenced rather than re-enumerated here.

## 2.0 Design Principles

The reference implementation SHALL follow the common design principles defined in ISL v0.1 §7 and the following implementation-specific principles.

### 2.1 Preserve Logical Architecture

The reference implementation MUST preserve the logical subsystem boundaries defined in ISL v2.0, even when implemented as a single process or local application. Combining modules for convenience MUST NOT allow bypass of specification parsing, canonical normalization, planning validation, runtime governance, deterministic validation, traceability recording, artifact repository admission, or state consistency.

### 2.2 Prefer Modular Monolith Before Distributed Complexity

The first reference implementation SHOULD begin as a modular monolith or small set of services with strong internal boundaries, supporting local-first development while preserving a path toward distributed deployment. The implementation MUST avoid hard dependencies that prevent later extraction of services, workers, integration layers, or stores.

### 2.3 Contracts Before Implementation Detail

The reference implementation MUST define explicit contracts between major modules before relying on implementation-specific coupling. Interfaces, request records, result records, state records, and event records SHOULD be defined independently of concrete adapters and storage mechanisms.

### 2.4 Deterministic Validation Is a Hard Boundary

Generated artifacts MUST pass through deterministic validation or a governance waiver before promotion. The implementation MUST NOT allow model output or agent output to bypass tool validation when validation is applicable.

### 2.5 Governance Is Runtime-Enforced

Governance MUST be implemented as an enforceable runtime decision service or module. It MUST NOT be limited to passive metadata, comments, or post-execution reporting.

### 2.6 Traceability Is Written During Execution

Traceability links MUST be created as lifecycle events occur. The implementation MUST NOT rely solely on after-the-fact reconstruction.

### 2.7 Local-First, Enterprise-Ready

The reference implementation SHOULD run locally with local stores, local tools, and local or configured model providers. The same logical architecture MUST also support migration to enterprise infrastructure.

## 3.0 Reference Implementation Layers

The reference implementation SHALL be organized into implementation layers.

| Layer | Responsibility |
| ----- | -------------- |
| Interface Layer | APIs, CLIs, UI endpoints, command handlers, external-facing contracts |
| Application Layer | Use cases, orchestration flows, service coordination |
| Domain Layer | ISL entities, task graphs, policies, state machines, validation rules |
| Runtime Layer | Scheduling, workers, queues, leases, locks, execution graph |
| Integration Layer | Model adapters, tool adapters, repository adapters, identity adapters |
| Persistence Layer | State stores, traceability graph stores, artifact metadata stores, audit stores |
| Observability Layer | Telemetry emission, logs, traces, metrics, alerts |
| Configuration Layer | Runtime, model, tool, governance, deployment, and environment configuration |

### 3.1 Layering Rules

* Interface components MUST NOT directly mutate persistence stores.
* Integration adapters MUST NOT contain domain policy logic except adapter-specific validation.
* Runtime components MUST use domain and application contracts to perform lifecycle actions.
* Persistence components MUST preserve records defined by ISL v2.2, v2.3, and v1.7.
* Observability components MUST observe but not decide lifecycle progression.
* Governance decisions MUST be enforced by application and runtime layers before controlled actions proceed.

* Each module MUST expose a defined public interface.
* Each module MUST hide internal implementation details behind contracts.
* Modules MUST NOT access another module's persistence tables or files directly unless explicitly authorized by the architecture.
* Modules SHOULD be independently testable.
* Modules SHOULD support dependency injection or equivalent composition to allow local and enterprise deployment profiles.
* A module MUST have one primary architectural responsibility.
* A source module MUST NOT depend on a deployable service project.
* Core domain modules MUST NOT depend on provider-specific adapters.
* `Aletheia.Common` MUST remain small and MUST NOT become a dumping ground for unrelated domain logic.
* A module that owns a state model MUST expose state transition contracts rather than allowing external direct mutation.

## 6.0 Service Topology and Interactions

The Execution Service is the operational coordinator. It consumes an executable construction plan, schedules tasks, invokes agents through the Agent module and the Model Integration Service, invokes deterministic tools through the Tool Integration Service, writes artifacts through the Artifact Service, records traceability through the Traceability Service, consults governance through the Governance Service, and emits telemetry through the Telemetry Service. It delegates reusable asset discovery and Reuse Decisions to the Reuse Registry Service, model invocation to the Model Integration Service, deterministic validation to the Tool Integration Service, artifact lifecycle operations to the Artifact Service, traceability operations to the Traceability Service, and governance decisions to the Governance Service.

### 6.1 Primary Service Interactions

| Source | Target | Purpose |
| ------ | ------ | ------- |
| Specification Service | SemanticModel Module | Normalize parsed specifications |
| Specification Service | Readiness Module | Evaluate readiness |
| Planning Service | SemanticModel Module | Read canonical graph |
| Planning Service | Reuse Registry Service | Reuse discovery and decision support |
| Planning Service | Traceability Service | Initialize planning traceability |
| Planning Service | Governance Service | Evaluate planning constraints |
| Execution Service | Planning Service | Accept executable plan |
| Execution Service | Governance Service | Check runtime authorization |
| Execution Service | Model Integration Service | Invoke reasoning models |
| Execution Service | Tool Integration Service | Invoke deterministic tools |
| Execution Service | Artifact Service | Admit and update artifacts |
| Execution Service | Traceability Service | Record runtime links |
| Execution Service | State Module | Commit runtime state transitions |
| Execution Service | Telemetry Service | Emit execution telemetry |
| Artifact Service | Tool Integration Service | Validate artifact content when required |
| Governance Service | Telemetry Service | Emit governance telemetry |
| Traceability Service | State Module | Record snapshots and integrity state |

### 6.2 Topology Rules

* The Execution Service MUST NOT directly invoke external model providers.
* The Execution Service MUST NOT directly invoke external deterministic tools.
* The Execution Service MUST NOT write stable artifacts without Artifact Service promotion.
* The Execution Service MUST NOT bypass Governance Service decisions.
* The Artifact Service MUST NOT promote artifacts without validation, traceability, and governance checks.
* Services MUST communicate through structured contracts.
* Services MUST preserve correlation identifiers.
* Services MUST respect ownership boundaries.
* Services MUST NOT bypass the Governance Service for governed actions.
* Services MUST NOT bypass the State Module for lifecycle state transitions.

## 7.0 Repository Layout

The repository is the long-lived home of the platform implementation. Its layout is an implementation control mechanism that reinforces the architecture: it separates core libraries from deployable services, contracts from adapters, and stable implementation from experiments, and it keeps local-first execution and enterprise evolution both possible.

### 7.1 Repository Organization Principles

* **Architecture-Aligned Layout** — The repository MUST align with the logical architecture in ISL v2.0 and this document. A contributor SHOULD be able to infer a module's responsibility from its repository location and package name.
* **Separation of Libraries and Services** — Reusable platform logic MUST be placed in source libraries or modules; deployable processes MUST be placed in service projects. A service MAY compose multiple libraries, but reusable domain logic MUST NOT live only inside service entry points.
* **Contracts Before Adapters** — Shared contracts, schemas, request and response records, error records, and event records MUST be separated from provider-specific adapters. Model provider adapters, tool adapters, repository adapters, identity adapters, and telemetry exporters MUST depend on stable contracts; stable contracts MUST NOT depend on adapters.
* **Local-First Without Architectural Collapse** — The repository MUST support running locally as a modular monolith, local service set, or containerized local deployment, using the same contracts and control boundaries as larger deployments.
* **Test Structure Mirrors Implementation** — Tests SHOULD be organized to mirror implementation modules and services.
* **Experimental Isolation** — Experimental work MUST be isolated from core implementation modules until it satisfies promotion criteria.
* **Automation Is Part of the Product** — Build scripts, deployment manifests, test automation, validation automation, and developer tooling MUST be versioned with the repository.

### 7.2 Root Repository Structure

| Path | Purpose |
| ---- | ------- |
| `/docs` | ISL documents, architecture documentation, contributor guidance, governance guidance |
| `/examples` | Example ISL specifications and reference construction scenarios |
| `/assets` | Static diagrams, images, sample payloads, and non-code assets |
| `/src` | Core platform libraries and modules |
| `/services` | Deployable platform services |
| `/contracts` | Shared schemas, API contracts, event contracts, and generated contract artifacts |
| `/adapters` | Provider-specific model, tool, repository, identity, and telemetry adapters |
| `/tests` | Automated tests |
| `/experiments` | Isolated experimental modules and prototypes |
| `/infra` | Infrastructure, deployment, container, local orchestration, and environment assets |
| `/build` | Build scripts, packaging scripts, release automation, and CI configuration |
| `/tools` | Developer tools, repository utilities, validation scripts, and local support tools |
| `/samples` | Sample generated outputs, sample artifacts, and demonstration data |
| `/config` | Versioned non-secret configuration templates |
| `/schemas` | Machine-readable schemas for ISL, canonical entities, contracts, and records |
| `/artifacts` | Local-only generated platform artifacts when needed for development; SHOULD NOT contain production generated systems |

Root layout rules:
* The repository MUST contain `/src`, `/services`, `/tests`, `/docs`, and `/build`.
* The repository SHOULD contain `/contracts`, `/schemas`, `/examples`, `/infra`, and `/config`.
* Secrets MUST NOT be stored in the repository.
* Generated output under `/artifacts` MUST be local, transient, or clearly classified. Production generated systems MUST be stored in artifact repositories governed by ISL v2.3, not in the platform implementation repository.

### 7.3 Source Module Layout

The `/src` directory contains the stable platform libraries. The complete module catalog — module names, repository paths under `/src`, responsibilities, and the module rules — is defined once in §4.0 and applies unchanged here. The standard library directory is `/src/Aletheia.{ModuleName}`, including the shared primitives module `/src/Aletheia.Common`.

A source module MUST have one primary architectural responsibility, MUST NOT depend on a deployable service project, and a core domain module MUST NOT depend on provider-specific adapters.

| Path | Purpose |

Contract and schema rules:

### 7.5 Adapter Layout

The `/adapters` directory contains technology-specific and provider-specific integrations, deliberately separated from core modules.

| Path | Purpose |
| ---- | ------- |
| `/adapters/models` | Model provider adapters |
| `/adapters/tools` | Deterministic tool adapters |

| `/adapters/storage` | Persistence and storage adapters |
| `/adapters/secrets` | Secret manager adapters |
| `/adapters/deployment` | Deployment environment adapters |

Adapter rules:
* Adapters MUST depend on platform contracts and relevant core abstractions.
* Core modules MUST NOT depend on adapter implementations.
* Adapters MUST declare supported contract versions and expose health and capability metadata where applicable.
* Adapters used in enterprise or regulated deployments SHOULD have integration tests or simulators.

### 7.6 Deployable Service Layout

The `/services` directory contains the deployable services. The complete service catalog — service names, service project paths under `/services`, responsibilities, and the service deployment rules — is defined once in §5.0 and applies unchanged here.

Optional service projects under `/services` include `/services/Aletheia.WorkerService` (generic runtime worker host), `/services/Aletheia.AgentWorker` (agent-specific worker), `/services/Aletheia.ToolWorker` (tool-specific worker), `/services/Aletheia.RepositoryWorker` (repository operation worker), `/services/Aletheia.AdminService` (administrative APIs and operational controls), and `/services/Aletheia.DashboardService` (operational dashboard backend). Services MUST expose structured APIs or message contracts, MUST use source modules for domain logic, MUST authenticate external calls in team, enterprise, distributed, and regulated deployments, and MUST emit telemetry for lifecycle operations.

### 7.8 Documentation, Examples, Samples, and Experiments Layout

Documentation (`/docs`) MAY be organized as `/docs/specification`, `/docs/architecture`, `/docs/contributing`, `/docs/governance`, `/docs/runtime`, `/docs/repository`, `/docs/adapters`, `/docs/deployment`, `/docs/security`, `/docs/observability`, `/docs/runbooks`, and `/docs/decisions`. Documentation MUST identify applicable ISL versions, and MUST NOT contain secrets. Architecture decision records SHOULD be created for significant repository or service topology changes.

Examples and samples (`/examples`, `/samples`) support learning, validation, and scenario testing. `/examples` SHOULD include `/examples/specifications`, `/examples/canonical`, `/examples/plans`, `/examples/scenarios`, `/examples/governance`, and `/examples/runtime`. `/samples` SHOULD include `/samples/generated-artifacts`, `/samples/tool-results`, `/samples/model-outputs`, `/samples/telemetry`, and `/samples/repository`. Examples SHOULD be executable by scenario tests, SHOULD include expected outputs, and MUST NOT contain real secrets, regulated data, or proprietary production content.

Experiments (`/experiments`) allow innovation without destabilizing the stable platform. Experimental work MUST NOT be imported into `/src` or `/services` unless ownership is assigned, purpose and scope are documented, tests exist, contracts are defined where applicable, governance review is completed when risk requires it, compatibility with current ISL versions is documented, and security implications are reviewed where applicable. An experiment MUST carry metadata identifying `experiment-id`, `experiment-name`, `owner`, `purpose`, `affected-subsystems`, `risk-tier` (see ISL v0.1 §6.2), `status`, `promotion-target` (conditional), `evaluation-evidence` (conditional), and `created-at`.

### 7.9 Infrastructure, Build, Automation, and Configuration Layout

The `/infra` directory contains deployment assets for local, team, enterprise, distributed, and regulated modes. `/infra` SHOULD be organized as `/infra/local`, `/infra/container`, `/infra/kubernetes`, `/infra/cloud`, `/infra/enterprise`, `/infra/regulated`, `/infra/observability`, `/infra/identity`, `/infra/secrets`, and `/infra/storage`. Infrastructure assets MUST be environment-scoped, MUST NOT contain plaintext secrets, and MUST identify required services and stores. Regulated deployment assets MUST identify governance, audit, retention, and security controls.

The `/build` and `/tools` directories contain reproducible automation. `/build` SHOULD be organized as `/build/scripts`, `/build/ci`, `/build/release`, `/build/validation`, and `/build/templates`; `/tools` as `/tools/dev`, `/tools/schema`, `/tools/contracts`, `/tools/repository`, `/tools/testdata`, and `/tools/security`. Build automation MUST support clean build from source. Test automation MUST support running unit, contract, integration, and scenario tests independently. Repository validation SHOULD check required directories, module naming, contract versions, schema validity, and forbidden secret patterns. Release automation MUST preserve version metadata.

The `/config` directory contains versioned non-secret configuration templates (e.g., `/config/local`, `/config/test`, `/config/team`, `/config/enterprise`, `/config/regulated`, `/config/runtime`, `/config/models`, `/config/tools`, `/config/governance`, `/config/telemetry`). Configuration templates MUST be versioned, MUST NOT contain secrets, and runtime secrets MUST be resolved externally. Configuration changes affecting runtime, governance, model routing, tool execution, or repository promotion SHOULD have review requirements.

### 7.10 Package and Dependency Structure

The preferred dependency direction is: `Aletheia.Common` → contracts and schemas → domain modules → application modules → runtime modules → services → adapters → infrastructure and deployment assets.

Prohibited dependencies:
* Core modules MUST NOT depend on deployable services.
* Core domain modules MUST NOT depend on provider-specific adapters.
* Governance, traceability, and state modules MUST NOT depend on runtime worker implementations.
* Contracts MUST NOT depend on services.
* Adapters MUST NOT be required to run unit tests for core domain modules.

Dependency rules:
* Dependency direction MUST be validated by automated checks where practical.
* Circular dependencies between source modules MUST NOT be permitted.
* A module dependency MUST be justified by an architectural relationship.
* Experimental modules MUST NOT be dependencies of stable modules.

Persistence rules:
* Lifecycle-critical records MUST be persisted durably.
* Governance audit records MUST be immutable or correction-only.

* Artifact metadata MUST remain consistent with artifact content.
* Runtime state MUST support recovery after interruption.
* Telemetry MUST NOT be treated as authoritative state.

## 12.0 Runtime Implementation Architecture

The runtime implementation MUST provide task execution according to ISL v2.0.

### 12.1 Runtime Components

| Component | Responsibility |
| --------- | -------------- |

## 24.0 Reference Implementation Workflow

The reference implementation MUST support the following workflow.

1. Receive authored specification.
2. Parse and structurally validate specification.
3. Normalize into canonical semantic model.
4. Evaluate readiness.
5. Generate construction task graph.
6. Validate construction plan.
7. Record planning traceability.
8. Perform governance execution admission check.
9. Initialize execution graph.
10. Schedule eligible tasks.
11. Invoke agents through agent and model contracts.
12. Admit generated artifacts into repository.
13. Invoke deterministic tools for validation.
14. Record validation results.
15. Trigger bounded repair when validation fails.
16. Promote valid and traced artifacts to stable state.
17. Create traceability snapshots.
18. Produce telemetry and audit records.
19. Prepare deployment artifacts when required.
20. Produce completion report.

The workflow MUST stop or pause when readiness, governance, validation, traceability, or state consistency conditions fail, MUST preserve evidence for every lifecycle decision, and MUST be recoverable after interruption.

## 25.0 Implementation Modes and Service Topology Variants

### 25.1 Implementation Modes

The reference implementation MUST support progressive deployment modes.

| Mode | Description |
| ---- | ----------- |
| local-library | All modules invoked in-process by tests, CLI, or local host |
| local-service | Core services run locally as one process or small service set |
| containerized-local | Services run locally in containers |
| team-service | Shared services support multiple users or projects |
| distributed-workers | Runtime workers scale independently |
| enterprise-services | Services integrate with enterprise identity, telemetry, storage, and governance |
| regulated-profile | Deployment applies high-assurance audit, security, and retention controls |

Each mode MUST preserve logical boundaries. Moving from one mode to another MUST NOT require rewriting domain contracts. Distributed modes MUST use durable queues, leases, locks, and state stores. Enterprise and regulated modes MUST enforce identity, governance, audit, traceability, and retention controls.

### 25.2 Local-First Service Topology

Local modes include `in-process`, `local-service-set`, `containerized-local`, and `hybrid-local` (core platform runs locally while configured model or tool providers may be external). Local-first mode MUST support specification parsing, canonical normalization, reuse registry operations, planning, execution, artifact repository operations, traceability, governance, and telemetry. Local-first mode MAY use simplified stores but MUST preserve service and module boundaries through internal contracts even when deployed in-process.

### 25.3 Enterprise Service Topology

Enterprise services may be grouped as Control Plane (Governance, Configuration, Planning, Reuse Registry, Scheduler components), Execution Plane (Execution Service, Worker Service, Agent Worker, Tool Worker), Integration Plane (Model Integration Service, Tool Integration Service, repository adapters, identity adapters), Data Plane (state, artifact, traceability, governance, telemetry stores), Observability Plane (Telemetry Service, dashboards, alerts, exporters), and Administration Plane (Admin Service, operational APIs, deployment controls). Enterprise topology MUST authenticate service-to-service communication, support durable state stores and telemetry aggregation, isolate projects and tenants where configured, and preserve governance and traceability consistency across service boundaries.

### 25.4 Worker Topology

Worker types include General, Agent, Model, Tool, Repository, Governance, and Telemetry workers. Workers MUST register capabilities, claim work through leases, emit heartbeats, respect project, tenant, and environment isolation, NOT perform work outside declared capabilities, and release locks and leases according to runtime rules.

### 25.5 Gateway and Interface Topology

External integrations MUST be accessed through the integration layers or approved adapters. Integration layer contracts MUST be provider-neutral, SHALL record telemetry, and SHALL produce structured error records on failure. The reference implementation MAY expose CLIs, REST APIs, gRPC APIs, a message bus, a Web UI, an Admin API, and a Query API. External APIs MUST enforce authentication and authorization; internal APIs SHOULD preserve correlation context; asynchronous messages MUST include idempotency or deduplication identifiers where needed; APIs that mutate lifecycle state MUST emit state events.

## 26.0 Repository Governance and Validation

### 26.1 Governed Repository Changes

The following changes SHOULD require review: adding a new core source module; adding a new deployable service; changing contract layout; changing schema versioning rules; moving domain logic between modules; adding a new integration or gateway type; adding enterprise deployment assets; changing dependency direction; promoting an experiment; removing or archiving stable modules. A repository structure change MUST preserve architectural boundaries; a new module MUST declare ownership and responsibility; a new service MUST declare API contracts and dependencies.

### 26.2 Repository Validation

The repository SHOULD include automated validation checking that required directories and modules exist, required service projects exist or are intentionally omitted by profile, contracts are versioned, schemas validate, dependency rules are not violated, tests exist for required modules, infrastructure files contain no plaintext secrets, documentation identifies supported ISL versions, experiments are not referenced by stable modules, service topology manifests are valid, and build scripts run from a clean checkout.

Repository validation records MUST include `repository-validation-id`, `repository-version`, `validation-profile` (a deployment profile), `checks-performed`, `validation-outcome` (see ISL v0.1 §6.5), `findings` (conditional), `validated-at`, and `validated-by`. A release candidate SHOULD NOT be produced if repository validation fails. Regulated profile validation MUST fail when required governance, audit, security, or retention assets are missing. Warnings MUST be reviewed before release when they affect architecture, security, or governance.

### 26.3 Service Topology Manifest

The repository SHOULD define a machine-readable Service Topology Manifest. The manifest MUST identify required services and stores, MUST identify external dependencies, and MUST identify queues, workers, leases, locks, and durable state stores for distributed topologies, and governance, audit, retention, and security controls for regulated topologies. Manifest fields include `topology-manifest-id`, `topology-name`, `topology-version`, `deployment-profile`, `services`, `modules`, `adapters` (conditional), `stores`, `queues` (conditional), `external-dependencies` (conditional), governance/telemetry/security profile identifiers (conditional), and `created-at`.

## 27.0 Versioning, Release, Migration, and Evolution

The repository MUST support versioned releases. A release MUST identify supported ISL versions, contract versions, and schema versions; SHOULD include repository validation evidence; and SHOULD include migration notes when repository layout changes.

The repository layout MAY evolve: new directories MAY be added when they represent clear architectural responsibilities; existing directories MUST NOT be repurposed in a way that changes their meaning without migration documentation; module splits MUST preserve public contracts or provide migration paths; service extraction from a modular monolith MUST preserve the same contracts; deprecated modules MUST remain discoverable until removal is governed and documented. Migration records capture `migration-record-id`, `migration-type`, `affected-paths`, `affected-contracts` (conditional), `compatibility-impact`, `migration-guidance`, `approved-by` (conditional), and `recorded-at` using ISO 8601.

## 30.0 Conformance Requirements

### 30.1 Module Conformance

A module conforms to ISL v3.0 if it implements a defined responsibility, exposes structured contracts, preserves logical boundaries, records required state and telemetry, enforces applicable governance, validation, traceability, and security rules, and is testable through unit or contract tests.

### 30.2 Service Conformance

A service conforms to ISL v3.0 if it exposes defined service responsibilities, uses structured APIs, enforces access control where required, records lifecycle actions, emits telemetry, preserves correlation identifiers, and does not bypass lower-level module contracts. A service topology conforms if it identifies services and dependencies, preserves control boundaries, routes model interactions through the Model Integration Service, routes deterministic tool interactions through the Tool Integration Service, routes reusable asset discovery and Reuse Decisions through the Reuse Registry Service or equivalent module, routes artifact lifecycle operations through the Artifact Service, routes governed actions through the Governance Service, routes traceability writes through the Traceability Service, preserves correlation identifiers, and supports the claimed deployment profiles.

### 30.3 Persistence Conformance

A persistence implementation conforms to ISL v3.0 if it stores lifecycle-critical records durably, preserves version context, supports state recovery, supports traceability and governance retention, protects audit records, and maintains artifact metadata and content consistency.

### 30.4 Repository Conformance

A platform implementation repository conforms to ISL v3.0 if it includes required root directories, separates source modules from services, separates contracts from adapters, separates stable implementation from experiments, contains tests organized by test type or module, contains documentation for architecture and operation, contains build automation and non-secret configuration templates, supports local-first execution and repository validation, supports contract and schema validation, supports module and service evolution, supports security checks, supports release versioning, supports service topology manifests, and prevents experiments from becoming hidden production dependencies.

### 30.5 Reference Implementation Conformance

A reference implementation conforms to ISL v3.0 if it implements the required core modules or equivalent responsibilities, supports local-first execution, supports reusable asset registry behavior and reuse decision enforcement, preserves logical subsystem boundaries, supports the Model Integration and Tool Integration layers, supports execution runtime behavior, artifact repository lifecycle, traceability graph recording, governance enforcement, state persistence and recovery, observability and telemetry, structured contracts, and passes the validation criteria defined below.

### 30.6 Validation Criteria

A reference implementation is valid when it can demonstrate specification parsing, canonical normalization, readiness evaluation, construction planning, execution admission, task scheduling, agent invocation, model routing and output normalization, artifact admission, deterministic validation, bounded repair, traceability link creation, governance check enforcement, telemetry emission, state persistence, recovery after interruption, artifact promotion, and completion reporting. Validation evidence MUST be recorded; scenario validation SHOULD use a minimal system before expanding to complex systems; a failed validation criterion MUST produce an implementation conformance finding.
