# ALETHEIA Specification Language (ISL) v2.3
# Observability, Telemetry, and Deployment
**Status:** Normative
**Release:** r3
**Depends On:** ISL v0.0, ISL v0.1, ISL v1.x
**Supersedes:** ISL r2 v2.6 The Observability and Telemetry Model, ISL r2 v2.7 The Enterprise Deployment and Scaling Model
**Document Type:** Platform Model Specification

---

## 1.0 Scope

This document defines the Observability and Telemetry Model and the Enterprise Deployment and Scaling Model for the ALETHEIA platform.

The observability portion establishes how platform activity is measured, emitted, correlated, stored, queried, visualized, alerted, protected, and used for operational understanding. It is the single authoritative home for the complete telemetry event, metric, and trace catalog. All other ISL r3 documents reference this document rather than defining their own telemetry lists.

The deployment portion establishes how the platform itself is deployed, scaled, isolated, operated, secured, monitored, recovered, and governed across local, team, enterprise, distributed, hybrid, and cloud-integrated environments. It does not define the deployment of systems generated by ALETHEIA, except where platform deployment capabilities affect deployment preparation, artifact repositories, governance, observability, or operational controls.

Shared conventions — including normative language, field requirement levels, identifier formats, shared enums, design principles, the common error model, the common telemetry model, and the conformance framework — are defined in ISL v0.1 and are incorporated by reference. Domain documents MUST NOT redefine them.

## 2.0 Observability Principles

1. **Observability Is Core.** Observability MUST be integrated into platform subsystems and MUST NOT be treated as optional debugging instrumentation. Every major lifecycle action SHOULD emit telemetry sufficient to monitor execution and diagnose failures.
2. **Telemetry Is Not Audit.** Telemetry supports monitoring and diagnostics. It MUST NOT replace immutable governance audit logs, traceability records, artifact metadata, validation evidence, or state records. Where an action is audit-relevant, both telemetry and audit/state records MAY exist, but the audit/state record remains authoritative.
3. **Correlation Is Mandatory.** Telemetry MUST include correlation identifiers sufficient to connect events to specifications, plans, executions, tasks, artifacts, agents, tools, models, governance checks, and traceability records where applicable. Uncorrelated telemetry SHOULD be treated as degraded observability.
4. **Structured Telemetry Is Required.** Telemetry used for monitoring, alerting, dashboards, or automated analysis MUST be structured. Free-form logs MAY exist but MUST NOT be the only telemetry source for lifecycle-critical operations.
5. **Security Is Preserved.** Telemetry MUST NOT leak secrets, restricted context, sensitive artifacts, raw model prompts, confidential policy data, credentials, or regulated data unless explicitly authorized by governance.
6. **Telemetry Is Actionable.** Telemetry SHOULD support operational action and SHOULD identify affected targets, severity, likely cause, and remediation path when determinable.
7. **OpenTelemetry Alignment.** A conforming platform SHOULD align telemetry concepts with OpenTelemetry traces, metrics, logs, attributes, resources, context propagation, and semantic conventions.

The common Telemetry Event structure from ISL v0.1 §9.1 applies and is extended by the schema in §4.

## 3.0 Telemetry Signal Types

| Signal Type | Purpose |
| ----- | ----- |
| `event` | Records a discrete lifecycle or operational occurrence |
| `trace` | Records an end-to-end operation composed of spans |
| `span` | Records a timed unit of work within a trace |
| `metric` | Records a numerical measurement or aggregate |
| `log` | Records a diagnostic or operational record |
| `alert` | Records a notification generated by an alert rule |
| `profile` | Records a performance profile or resource breakdown |
| `heartbeat` | Records liveness of workers, services, or integrations |

A lifecycle transition SHOULD emit an event. A long-running operation SHOULD emit a trace and spans. Repeated measurements SHOULD be represented as metrics. Human-readable diagnostic details MAY be logs, but lifecycle state MUST be represented structurally. Worker liveness SHOULD be represented through heartbeat telemetry.

## 5.0 Correlation and Context Propagation

The platform SHOULD propagate `correlation-id`, `trace-id`, `span-id`, `parent-span-id`, and the entity identifiers listed in §4 (specification, plan, execution graph, task, work item, artifact, reusable asset, reuse decision, construction boundary, connection context, agent/model/tool invocation, governance check, and repository operation).

A construction task execution SHOULD create or continue a trace. Agent, model, tool, artifact, validation, repair, and governance events caused by a task SHOULD share the task correlation context. A repair cycle SHOULD preserve correlation with the failed validation result and failed artifact. A reuse-gated generation task SHOULD preserve correlation across Reuse Discovery, Reuse Decision, selected reusable assets, model invocations, artifact admission, validation, and traceability. A boundary-scoped task SHOULD preserve correlation across Construction Boundary, Connection Context, context minimization, drift findings, and downstream actions. A model fallback SHOULD preserve correlation with the original model invocation. A telemetry event without required correlation identifiers SHOULD produce an observability warning.

## 6.0 Trace and Span Model

### 6.1 Standard Trace Types

| Trace Type | Description |
| ----- | ----- |
| `specification-processing-trace` | Specification intake through canonical validation |
| `readiness-evaluation-trace` | Readiness evaluation and transition |
| `planning-trace` | Construction plan generation and validation |
| `execution-trace` | End-to-end construction execution |
| `task-execution-trace` | Runtime execution of one task |
| `agent-collaboration-trace` | Multi-agent collaboration session |
| `model-invocation-trace` | Model routing, context control, invocation, normalization |
| `reuse-discovery-trace` | Reusable asset search, fitness assessment, and Reuse Decision |
| `context-boundary-trace` | Construction Boundary, Connection Context, context minimization, and drift checks |
| `tool-invocation-trace` | Tool selection, invocation, result normalization |
| `validation-trace` | Validation execution and result handling |
| `repair-trace` | Repair cycle from failure to revalidation |
| `artifact-lifecycle-trace` | Artifact admission through promotion or archival |
| `governance-trace` | Governance check, approval, waiver, override, escalation |
| `deployment-preparation-trace` | Deployment preparation and authorization support |

### 6.2 Span Schema

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| trace-id | string | REQUIRED | Trace identifier |
| span-id | string | REQUIRED | Span identifier |
| parent-span-id | string | CONDITIONAL | Parent span |
| span-name | string | REQUIRED | Span name |
| span-kind | enum | REQUIRED | `internal`, `client`, `server`, `producer`, `consumer` |
| start-time | ISO 8601 | REQUIRED | Span start |
| end-time | ISO 8601 | CONDITIONAL | Span end |
| status | enum | REQUIRED | `unset`, `ok`, `error` |
| source-subsystem | string | REQUIRED | Subsystem emitting span |
| attributes | object | OPTIONAL | Span attributes |
| events | array | OPTIONAL | Span events |

End-to-end execution SHOULD produce an execution-trace. Every task SHOULD produce a task-execution-trace or span. Model and tool invocations SHOULD be represented as child spans of the agent or validation task that caused them. Trace status `error` MUST be set when the traced operation fails.

## 7.0 Metric Model

### 7.1 Metric Types and Record

Metric types are `counter`, `gauge`, `histogram`, `summary`, `rate`, and `ratio`. A Metric Record MUST include `metric-name`, `metric-type`, `value`, `timestamp`, `source-subsystem`, `retention-class`, and, when scoped, `specification-id` and `execution-graph-id`; it MAY include `unit` and `attributes`.

### 7.2 Required Metric Categories

The platform SHOULD collect metrics for:

* execution progress, task throughput, task failure rate
* repair iteration count, repair convergence rate
* agent invocation duration, agent output validation failure rate
* model invocation latency, model fallback rate
* tool invocation duration, tool failure rate
* reuse discovery duration, reuse decision outcome count, reusable asset hit rate
* context boundary drift count, connection context validation failure rate
* validation pass/fail rate, artifact promotion rate
* governance approval wait time
* queue depth, worker utilization, lock wait time
* repository conflict rate, artifact count by state, reusable asset dependent count
* telemetry ingestion failure rate, and the resource and telemetry-health metrics in §13 and §17.

## 8.0 Log Model

A Log Record MUST include `log-id`, `timestamp`, `severity` (`trace`, `debug`, `info`, `warn`, `error`, `fatal`), `source-subsystem`, `message`, `correlation-id`, and `redaction-status`; it MAY include `specification-id`, `execution-graph-id`, `task-id`, and `attributes`. Logs SHOULD be structured. Logs MUST NOT contain secrets. Logs containing restricted information MUST be redacted or access-controlled. Fatal logs SHOULD produce alert evaluation.

This section is the single authoritative catalog for the telemetry events, metrics, and traces emitted by ISL subsystems. Other ISL documents reference these event names rather than defining their own lists. A conforming platform SHOULD emit these events and SHOULD collect these metrics. All events use the common schema in §4 and the common telemetry model in ISL v0.1 §9.1.

### 9.10 Telemetry Rules

Telemetry events SHOULD include correlation identifiers linking them to state records, events, tasks, executions, artifacts, governance actions, or recovery actions. Telemetry MUST NOT expose restricted memory, state, or artifact content to unauthorized observers. State transitions SHOULD also be recorded as immutable state events per ISL v2.2.

## 10.0 Performance and Resource Telemetry

The platform SHOULD collect CPU, memory, disk, and network utilization by subsystem; queue processing latency; worker utilization; model and tool invocation latency; repository operation duration; governance approval wait duration; and telemetry ingestion, processing, and export latency.

The platform SHOULD define alerts for sustained high CPU usage, sustained high memory usage, queue backlog growth, worker starvation, model provider saturation, tool execution saturation, repository storage exhaustion, telemetry ingestion backlog, and telemetry storage exhaustion.

## 11.0 Alerting Model

### 11.1 Alert Severity

| Severity | Meaning |
| ----- | ----- |
| `critical` | Immediate action required; execution, security, governance, or data integrity at risk |
| `high` | Significant issue requiring timely intervention |
| `medium` | Degraded condition requiring monitoring or planned intervention |
| `low` | Minor issue or warning |
| `informational` | Useful operational signal |

### 11.2 Alert Rule

An Alert Rule MUST include `alert-rule-id`, `alert-name`, `signal-source` (`event`, `metric`, `log`, `trace`), `condition`, `severity`, `scope` (`global`, `project`, `specification`, `execution`, `subsystem`), `evaluation-window`, and `status` (`active`, `disabled`, `deprecated`); it MAY include `threshold`, `notification-targets`, `suppression-policy`, and `runbook-reference`.

### 11.3 Required Alert Conditions

The platform SHOULD define alert rules for repeated task failures; repair iteration threshold reached; execution halted; execution recovery failed; governance approval timeout; governance audit write failure; critical security finding; traceability integrity failure; repository integrity failure; model fallback exhausted; tool timeout spike; worker heartbeat failure; queue backlog threshold exceeded; telemetry ingestion failure; and restricted context exposure attempt.

### 11.4 Alert Rules

Critical alerts SHOULD notify operations and governance roles where applicable. Alerts MUST include affected identifiers when determinable. Alerts SHOULD include runbook or required-action references. Alert suppression MUST NOT hide critical unresolved conditions.

## 12.0 Operational Dashboards

A conforming enterprise platform SHOULD provide dashboards for platform health, execution progress, task queues and workers, agent activity, model usage and failures, tool validation outcomes, artifact lifecycle state, governance status, traceability integrity, repair cycles, repository integrity, resource utilization, and alert summary.

Dashboards MUST respect access control and MUST NOT display restricted telemetry content to unauthorized viewers. Dashboards SHOULD provide drill-down from summary metrics to correlated events, traces, logs, and state records. Governance dashboards SHOULD distinguish telemetry from authoritative audit records.

## 13.0 Telemetry Storage, Retention, and Quality

### 13.1 Telemetry Store

Telemetry storage SHOULD support event, metric, trace, log, and alert-history storage; query by correlation-id, specification-id, execution-graph-id, task-id, artifact-id, and time range; access control; retention-policy enforcement; and export to external observability systems.

Retention classes are `transient`, `operational`, `audit-support`, and `archival`. Telemetry supporting High or Critical risk execution SHOULD be retained longer than telemetry for Standard systems. Telemetry linked to governance audit write failure, security finding, deployment authorization, or execution failure SHOULD be retained as `audit-support` or `archival`. Telemetry retention MUST NOT conflict with privacy, security, or data minimization requirements.

### 13.2 Access Control, Redaction, and Privacy

Telemetry access MUST be controlled by role, scope, sensitivity, and purpose. Restricted telemetry MUST require explicit authorization. Telemetry exports MUST enforce redaction and filtering policies. Raw model prompts, raw context packages, secrets, and restricted artifact contents MUST NOT be exposed through telemetry dashboards unless explicitly authorized.

Telemetry processors MUST redact secrets, credentials, tokens, private keys, restricted personal data, raw restricted prompts or context, and sensitive infrastructure details when policy requires. Redaction MUST preserve enough metadata for diagnosis when possible. Telemetry collection SHOULD follow data minimization. Telemetry containing personal data MUST be classified and governed. Telemetry used for continuous improvement MUST be aggregated or anonymized where required by policy.

### 13.3 Telemetry Quality

The platform SHOULD monitor completeness, timeliness, correlation coverage, schema validity, ingestion success rate, processing failure rate, export success rate, redaction success rate, storage availability, and query latency. The platform SHOULD collect telemetry events emitted, ingested, and dropped; telemetry processing latency; telemetry export failures; schema validation failures; uncorrelated telemetry count; redaction failures; and dashboard query latency.

Telemetry failure MUST NOT silently hide platform failure. Telemetry ingestion failure SHOULD produce local fallback logs or events when possible. A telemetry pipeline failure affecting critical alerts MUST itself produce a critical alert when detection is possible.

## 14.0 Telemetry Export and Integration

Telemetry MAY be exported to OpenTelemetry collectors, log aggregation systems, metrics platforms, tracing systems, SIEM systems, governance dashboards, enterprise monitoring platforms, and data warehouses for analytics. Telemetry export MUST obey governance policy. Restricted telemetry MUST be redacted, summarized, or blocked before export unless explicitly authorized. Export failures SHOULD produce telemetry and alerts. External export MUST preserve correlation identifiers.

### 14.1 OpenTelemetry Alignment

A platform claiming OpenTelemetry alignment SHOULD export traces, metrics, and logs in OpenTelemetry-compatible form, using consistent attribute names including `isl.specification.id`, `isl.specification.version`, `isl.plan.id`, `isl.execution.graph.id`, `isl.task.id`, `isl.artifact.id`, `isl.reusable_asset.id`, `isl.reuse_decision.id`, `isl.construction_boundary.id`, `isl.connection_context.id`, `isl.agent.invocation.id`, `isl.model.invocation.id`, `isl.tool.invocation.id`, `isl.governance.record.id`, `isl.traceability.node.id`, `isl.subsystem`, `isl.risk.tier`, and `isl.outcome`. Where OpenTelemetry lacks a semantic convention for ISL-specific concepts, ISL attributes MAY be used. OpenTelemetry export MUST NOT weaken ISL security, retention, or governance rules.

## 15.0 Deployment Design Principles

1. **Architecture Preservation Across Profiles.** Every deployment profile MUST preserve the logical subsystem boundaries defined in ISL v2.0. A local deployment MAY combine subsystems into one process but MUST still enforce the logical control boundaries for specification processing, planning, execution, governance, traceability, tool integration, model integration, artifact storage, state, and observability.
2. **Local-First Compatibility.** A conforming platform SHOULD support local-first deployment, where core functions run without mandatory external cloud services. Local-first compatibility MUST NOT prevent enterprise, hybrid, or cloud-integrated deployments.
3. **Independent Subsystem Scaling.** Enterprise deployments SHOULD scale subsystems independently. Scaling one subsystem MUST NOT weaken governance, traceability, validation, audit, or state consistency.
4. **Isolation Before Sharing.** A shared enterprise platform MUST isolate projects and tenants before sharing infrastructure resources.
5. **Durable State Before Distributed Execution.** A deployment MUST NOT enable distributed execution unless durable shared state, recoverable queues, lease and lock coordination, artifact repository consistency, and governance decision consistency are available.
6. **Governance Consistency Across Environments.** Governance rules MUST remain enforceable across deployment profiles. A task blocked in an enterprise deployment MUST NOT be allowed merely because it runs in a local, team, or cloud worker environment.
7. **Observability Is Required for Enterprise Operation.** Enterprise deployments MUST provide operational observability sufficient to monitor health, execution progress, failures, governance gates, resource saturation, and recovery behavior.

## 16.0 Deployment Profiles

### 16.1 Standard Deployment Profiles

| Profile | Purpose |
| ----- | ----- |
| `local-standalone` | Single-user local operation, experimentation, prototyping, and development |
| `team-shared` | Shared team environment with centralized coordination and repository integration |
| `enterprise-datacenter` | Organization-managed deployment integrated with enterprise infrastructure |
| `distributed-cluster` | Large-scale deployment with distributed workers and scalable runtime capacity |
| `hybrid-integrated` | Deployment combining local or enterprise control plane with approved external services |
| `regulated-enterprise` | Deployment for High or Critical risk environments requiring stronger security, audit, and governance |
| `multi-tenant-platform` | Shared enterprise platform supporting multiple teams, projects, or organizational units |

A deployment MUST declare its deployment profile. A deployment MAY support more than one profile if each profile’s requirements are satisfied. A deployment profile MUST identify enabled subsystems, storage dependencies, integration dependencies, governance mode, isolation mode, and recovery capability. A deployment claiming enterprise readiness MUST satisfy at least `enterprise-datacenter` profile requirements.

### 16.2 Deployment Profile Record

Each deployment MUST maintain a Deployment Profile Record with `deployment-profile-id`, `deployment-name`, `profile-type`, `environment-type` (`workstation`, `server`, `datacenter`, `cluster`, `private-cloud`, `public-cloud`, `hybrid`), `enabled-subsystems`, `control-plane-location`, `data-plane-locations`, `state-store-profile`, `artifact-repository-profile`, `governance-profile-id`, `isolation-mode` (`single-project`, `multi-project`, `multi-tenant`), `recovery-tier` (`none`, `basic`, `operational`, `enterprise`, `regulated`), `declared-at`, and `declared-by`, plus CONDITIONAL reuse, context-boundary, identity-provider, and telemetry profiles.

## 17.0 Deployment Topologies

### 17.1 Local Standalone

A local standalone deployment SHOULD include the Specification, Semantic Model, Planning, Agent Orchestrator, Model Integration, Construction, Tool Integration, Traceability, Governance (or local governance stub), Artifact Repository, State, and Memory subsystems, plus an observability emitter or local logs. It MAY use embedded or filesystem-backed stores and MAY run all subsystems in a single process. It MUST still enforce artifact validation, traceability, readiness, and governance rules required by its configured mode, and MUST NOT claim enterprise readiness unless it satisfies enterprise profile requirements.

### 17.2 Team Shared

A team shared deployment SHOULD provide centralized specification and canonical model storage, shared artifact repository integration, shared planning, shared execution runtime or worker pool, identity-aware access control, team-level governance configuration, shared telemetry and dashboards, branch and review workflow support, and state persistence sufficient for recovery. Team deployments MUST identify users and roles, preserve project-level artifact and state separation, SHOULD integrate with shared version control, and SHOULD support review workflows before artifact promotion or package generation.

### 17.3 Enterprise Datacenter

An enterprise datacenter deployment MUST provide durable state stores; controlled artifact repositories; identity and access management integration; governance engine integration; audit-capable governance records; traceability storage and query capability; runtime worker management; tool execution isolation; model provider governance; telemetry collection and alerting; backup and recovery procedures; and environment-specific configuration management. Enterprise deployments MUST separate control-plane and data-plane responsibilities logically, SHOULD support subsystem-level scaling, MUST protect governance, traceability, artifact, and state stores against unauthorized modification, and MUST define operational ownership for platform health, governance, security, and recovery.

### 17.4 Distributed Cluster

A distributed cluster deployment MUST provide durable execution queues; distributed worker registration; worker heartbeat monitoring; lease coordination; lock coordination; distributed state consistency; shared artifact repository access; traceability event ordering; governance decision consistency; model and tool workload isolation; and recovery after worker or node failure. Distributed execution MUST follow ISL v2.0 distributed runtime requirements. Cluster workers MUST NOT rely on local-only state for lifecycle decisions. Cluster deployments MUST detect stale leases and locks and MUST detect and halt split-brain execution. Cluster deployments MUST isolate project workspaces and artifact paths.

### 17.5 Hybrid and Cloud-Integrated

Hybrid deployments MAY use external services for model inference, artifact storage, telemetry storage, distributed compute, identity federation, policy evaluation, source control integration, package registries, and deployment environment integration. Hybrid deployments MUST declare which services are external; MUST enforce model and data governance before sending context, artifacts, telemetry, or metadata to external systems; MUST preserve local-first operation where the deployment profile requires it; MUST NOT externalize restricted data unless governance permits it; and MUST maintain traceability and audit continuity across local and external services.

### 17.6 Regulated Enterprise

A regulated enterprise deployment MUST provide strong identity and access control; role-based governance enforcement; separation-of-duties enforcement; immutable or integrity-protected audit logs; enhanced traceability retention; restricted model and tool profiles; evidence retention policies; security monitoring; deployment authorization controls; backup and disaster recovery; configuration change governance; and operational runbooks. High and Critical risk systems MUST use regulated deployment controls unless governance explicitly accepts a different profile. Regulated deployments MUST NOT use experimental models, tools, or plugins without explicit governance approval.

### 17.7 Multi-Project and Multi-Tenant Operation

The platform MUST support isolation for specifications; canonical models; construction plans; execution graphs; task queues; artifact repositories; traceability graphs; governance state; model context packages; tool workspaces; telemetry; configuration; secrets; and deployment preparation outputs. A Project Isolation Record MUST define `project-id`, artifact, state, traceability, governance, queue, and telemetry namespaces, `secret-scope`, and `isolation-level` (`logical`, `storage`, `network`, `process`, `cluster`).

A task from one project MUST NOT read or write another project’s artifacts unless governed cross-project access is explicitly authorized. A model context package from one tenant MUST NOT include another tenant’s data unless governance explicitly authorizes cross-tenant context. Traceability graphs MUST be scoped by project and specification version. Governance state MUST be isolated by project or tenant unless shared policy inheritance is explicitly configured. Telemetry dashboards MUST enforce project and tenant access controls.

### 17.8 Shared Infrastructure

Shared resources (runtime worker pools, model providers, tool execution pools, artifact storage, traceability, telemetry, governance, and secret managers) MUST enforce logical isolation at minimum. High and Critical risk systems SHOULD use stronger isolation (storage, process, network, or cluster). Shared workers MUST clean task workspaces between executions. Shared model providers MUST honor context sensitivity and data-retention profiles. Shared telemetry stores MUST restrict query access by project, tenant, and role.

## 18.0 Scaling

### 18.1 Scaling Units

| Scaling Unit | Scaling Driver |
| ----- | ----- |
| Specification Engine | Number and size of specifications |
| Semantic Model Engine | Canonical normalization workload |
| Planning Engine | Plan generation and adaptation workload |
| Runtime Scheduler | Number of active plans and tasks |
| Runtime Worker Pool | Task execution volume |
| Agent Orchestrator | Agent invocation volume |
| Model Integration Layer | Model routing and invocation volume |
| Model Provider Capacity | Reasoning workload and context size |
| Tool Integration Workers | Validation, test, scan, and package workload |
| Artifact Repository | Artifact count, package size, retention volume |
| Traceability Engine | Graph size and query workload |
| Governance Engine | Policy checks and approval volume |
| Telemetry Pipeline | Event, metric, trace, and log volume |
| State Store | State transition volume and query load |

A scaling unit MUST be scaled only in a way that preserves state consistency, traceability, governance enforcement, and artifact integrity. Runtime workers MAY scale horizontally when durable queues, leases, and locks are available. Model provider capacity MAY scale independently when routing and governance controls remain enforceable. Tool workers MAY scale independently when tool sandboxing and workspace isolation remain enforceable. Traceability query scaling MUST NOT corrupt traceability graph updates.

### 18.2 Scaling Policy

A Scaling Policy MUST include `scaling-policy-id`, `scaling-unit`, `scope`, `min-instances`, `max-instances`, `scale-out-triggers`, `scale-in-triggers`, `cooldown-period`, and `status`; it MAY include `resource-limits` and `governance-constraints`. Standard scale-out triggers include ready or delayed queue depth, worker utilization, model or tool invocation latency, validation backlog, telemetry ingestion backlog, traceability query latency, artifact repository operation latency, and governance check backlog.

Scaling policies MUST be versioned. Scaling policies for regulated environments MUST be governed. Scale-in MUST NOT terminate workers holding active leases unless draining or recovery behavior is safe. Scale-out MUST NOT exceed governance, cost, capacity, or risk-tier limits.

### 18.3 Capacity Planning

Enterprise deployments SHOULD maintain a capacity plan considering active projects, concurrent executions, task count and parallelism, artifact size, validation, model, tool, and telemetry volume, traceability graph size, retention, risk-tier, and recovery objectives. Regulated deployments SHOULD review capacity plans periodically. Capacity plans SHOULD be updated after major workload, retention, model, runtime, or governance changes.

## 19.0 High Availability

Availability tiers are `none`, `basic`, `operational`, `enterprise`, and `regulated`. Enterprise and regulated deployments SHOULD provide high availability for the State and Memory Store, Artifact Repository, Governance Engine, Traceability Store, Execution Queues, Runtime Scheduler, Telemetry Pipeline, Identity Integration, and Configuration Store.

High availability MUST preserve consistency. Failover MUST NOT cause duplicate task execution without lease recovery, and MUST NOT lose governance, traceability, artifact, validation, or state records. Governance Engine unavailability MUST block governed actions unless an approved degraded-mode policy exists.

## 20.0 Disaster Recovery, Backup, and Restore

### 20.1 Disaster Recovery

A deployment SHOULD define RPO, RTO, recovery scope, backup frequency, restore validation, and recovery authority. A Disaster Recovery Plan MUST include `disaster-recovery-plan-id`, `deployment-profile-id`, `recovery-tier`, `rpo`, `rto`, `protected-state-categories`, `backup-locations`, `restore-procedure-reference`, `validation-procedure-reference`, and `owner-role`; it MAY include `last-tested-at`. Enterprise deployments MUST back up state, governance, traceability, reusable asset registry records, reuse decisions, artifact metadata, artifact content, configuration, and audit records. Regulated deployments MUST periodically test DR procedures. A restored platform MUST run state, repository, traceability, and governance integrity checks before resuming execution.

### 20.2 Backup and Restore

Enterprise backups MUST include specification records; canonical models; construction plans; reusable asset records; reuse fitness assessments and Reuse Decisions; execution graphs; state event logs; artifact metadata and content; validation evidence; repair records; traceability graphs and snapshots; governance records and audit logs; model, tool, and platform configuration; telemetry retained as audit-support; and deployment profile records.

Restore MUST preserve identifiers, specification-version context, and audit immutability or integrity markers. Restore MUST NOT resume active execution until recovery validation passes. Restore into a different environment MUST revalidate external service bindings, secrets, identity mappings, and governance configuration.

## 21.0 Identity, Network, Secrets, and Configuration

### 21.1 Identity and Access Integration

Enterprise deployments SHOULD support centralized user authentication; service identity authentication; group-based authorization; role mapping to governance roles; project and tenant access scopes; audit attribution; emergency access procedures; and service-to-service authentication. Governance approvals MUST be attributable to authenticated identities. Service-to-service calls MUST use service identities. Role assignments MUST map to active identities or groups. Disabled or revoked identities MUST NOT authorize platform actions.

### 21.2 Network and Connectivity

Network zones include user-access, control-plane, worker, data, model, observability, and external-integration zones. Worker zones MUST NOT access governance or state stores except through approved service interfaces. External model providers MUST be accessed only through the Model Integration Layer. External tool services MUST be accessed only through the Tool Integration Layer. Artifact repositories MUST enforce authenticated and authorized access. Network paths carrying restricted data SHOULD be encrypted.

### 21.3 Secret and Configuration Management

Secrets MAY include model, tool, repository, database, identity, telemetry, and deployment credentials plus signing and encryption keys. Secrets MUST NOT be stored in specifications, agent context packages, telemetry logs, or generated artifacts unless explicitly authorized and protected. Secrets MUST be scoped by project, tenant, environment, and service identity. Secret access MUST be auditable. Secret rotation SHOULD be supported in enterprise deployments. Secret exposure MUST trigger security telemetry and runtime error handling.

Deployment configuration MUST be versioned. Changes affecting governance, runtime, model routing, tool execution, artifact repositories, or state stores MUST be auditable. Configuration changes during active execution MUST trigger impact evaluation when they may affect execution behavior.

## 22.0 Deployment Automation, Validation, and Promotion

### 22.1 Deployment Automation

Enterprise deployments SHOULD use automated processes for infrastructure provisioning, service deployment, configuration application, identity integration, secret injection, database migration, repository initialization, telemetry setup, health-check configuration, backup setup, and scaling-policy installation. A Platform Deployment Manifest MUST include `platform-deployment-manifest-id`, `deployment-profile-id`, `manifest-version`, `target-environment`, `subsystem-deployments`, `storage-bindings`, and `governance-profile-id`; it MAY include network, identity, secret, scaling-policy, and telemetry bindings. Automation MUST be repeatable, MUST NOT expose secrets in logs, MUST validate subsystem health after deployment, and SHOULD support rollback.

### 22.2 Environment Promotion

Environment stages include `local`, `dev`, `test`, `staging`, `prod`, and `regulated-prod`. Promotion to production MUST require deployment validation. Promotion to `regulated-prod` MUST require governance approval. Configuration promoted between environments MUST preserve version identity. Secrets MUST be rebound per environment and MUST NOT be copied blindly. External integrations MUST be revalidated in the target environment.

### 22.3 Deployment Validation

Deployment validation MUST check that required subsystems, state stores, artifact repositories, governance, traceability, and telemetry are reachable and operational; identity integration is functional; required tools and model providers are registered; worker pools and queues are healthy; backup configuration exists where required; security controls are configured; and deployment profile requirements are satisfied. A Deployment Validation Record MUST include `deployment-validation-id`, `deployment-profile-id`, `environment`, `validation-checks`, `validation-outcome` (`passed`, `failed`, `warning`), `validated-at`, and `validated-by`; it MAY include `findings` and `required-action`. A deployment MUST NOT claim a profile unless deployment validation passes for that profile. A failed deployment validation MUST block production or regulated use. Warnings MAY be accepted only when governance permits.

## 23.0 Governance, Degraded Mode, and Deployment Lifecycle

### 23.1 Governance Across Environments

A deployment MUST provide governance enforcement for readiness progression; execution start; restricted model and tool use; artifact promotion; waiver and override application; deployment authorization; configuration change; cross-project access; and regulated workload execution. Governance profiles MAY differ by environment, but weaker lower-environment governance MUST NOT authorize production activity. Production and regulated environments MUST use explicit governance profiles. Governance configuration changes MUST be versioned and audited. A deployment with unavailable Governance Engine MUST block governed actions unless a preapproved degraded-mode policy exists.

### 23.2 Degraded Mode

Degraded modes are `read-only`, `planning-only`, `execution-paused`, `telemetry-degraded`, `external-service-disabled`, and `recovery-only`. Degraded mode MUST be explicit and recorded in platform state. Governance-controlled actions MUST NOT proceed in degraded mode unless policy permits. `telemetry-degraded` mode MUST NOT hide audit, governance, traceability, or artifact records. `recovery-only` mode MUST NOT dispatch new construction work.

### 23.3 Deployment Lifecycle

Deployment lifecycle states are `proposed`, `provisioned`, `configured`, `validated`, `active`, `degraded`, `maintenance`, `suspended`, `failed`, and `retired`. A deployment MUST NOT enter `active` until validation passes. A `failed` deployment MUST NOT accept new execution requests. A `retired` deployment MUST preserve required records according to retention policy. Maintenance and degraded states MUST be visible in telemetry and operations dashboards.

## 24.0 Telemetry and Deployment Error Model

Observability, telemetry, and deployment errors use the common Error Record structure and error-class taxonomy from ISL v0.1 §8. The following extension error classes are registered under the shared taxonomy categories (`observability` and `deployment`) and MUST NOT replace the shared base model. Extension classes may subclass the common Error Record with domain-specific target identifiers.

### 24.1 Observability Errors (registered under `observability`)

| Error Class | Description | Default Handling |
| ----- | ----- | ----- |
| `observability-event-schema-invalid` | Telemetry event failed schema validation | warn or reject event |
| `observability-correlation-missing` | Required correlation identifier missing | warn |
| `observability-ingestion-failed` | Telemetry collector failed to ingest event | retry or fallback |
| `observability-processing-failed` | Telemetry processor failed | retry or alert |
| `observability-redaction-failed` | Redaction failed for sensitive telemetry | block export and alert |
| `observability-export-failed` | Export to external system failed | retry and alert |
| `observability-storage-unavailable` | Telemetry store unavailable | fallback or alert |
| `observability-query-failed` | Telemetry query failed | warn or alert |
| `observability-alert-evaluation-failed` | Alert rule evaluation failed | alert operations |
| `observability-dashboard-unavailable` | Dashboard unavailable | warn or alert |
| `observability-retention-violation` | Telemetry retained too long or deleted too early | escalate |
| `observability-unauthorized-access` | Unauthorized telemetry access attempted | block and escalate |
| `observability-critical-alert-suppressed` | Critical alert suppressed improperly | escalate |

### 24.2 Deployment Errors (registered under `deployment`)

| Error Class | Description | Default Handling |
| ----- | ----- | ----- |
| `deployment-profile-invalid` | Deployment profile incomplete or invalid | block activation |
| `deployment-validation-failed` | Deployment validation failed | block activation |
| `deployment-subsystem-unavailable` | Required subsystem unavailable | block or degraded mode |
| `deployment-state-store-unavailable` | State store unavailable | halt execution |
| `deployment-artifact-repository-unavailable` | Artifact repository unavailable | halt artifact operations |
| `deployment-governance-unavailable` | Governance unavailable | block governed actions |
| `deployment-traceability-unavailable` | Traceability unavailable | block execution completion |
| `deployment-identity-integration-failed` | Identity integration failed | block user and approval actions |
| `deployment-secret-resolution-failed` | Required secret unavailable | block affected subsystem |
| `deployment-network-policy-violation` | Network boundary violated | block and escalate |
| `deployment-scaling-limit-reached` | Scaling limit reached | alert and throttle |
| `deployment-worker-pool-exhausted` | No workers available | queue or scale out |
| `deployment-model-provider-unavailable` | Model provider unavailable | fallback or block |
| `deployment-tool-pool-unavailable` | Tool workers unavailable | queue or block validation |
| `deployment-backup-failed` | Backup failed | alert and escalate |
| `deployment-restore-failed` | Restore failed | halt and escalate |
| `deployment-isolation-violation` | Project or tenant isolation violated | halt and escalate |
| `deployment-telemetry-pipeline-failed` | Telemetry pipeline failed | degraded mode or alert |
| `deployment-configuration-drift` | Runtime configuration differs from declared manifest | block or reconcile |

### 24.3 Error Record

All errors use the common Error Record from ISL v0.1 §8.1. Deployment errors extend it with fields identifying `deployment-profile-id`, `environment`, `subsystem`, `project-id`, and `tenant-id`; observability errors add `affected-signal-type` and `affected-record-id`; default handling is captured through the common `required-action` field.

## 25.0 Conformance

### 25.1 Telemetry Event Conformance

A telemetry event conforms to this document if it includes the required common schema fields, uses a defined event category, includes correlation-id, includes specification and execution identifiers where applicable, includes reusable asset, Reuse Decision, Construction Boundary, and Connection Context identifiers where applicable, and declares severity, redaction status, and retention class, without unauthorized sensitive content.

### 25.2 Observability Subsystem Conformance

An observability subsystem conforms if it can collect structured events, metrics, traces and spans, and structured logs; preserve correlation identifiers; apply redaction and access controls; store telemetry according to retention rules; evaluate alert rules; expose dashboards or query interfaces; export telemetry where configured; monitor telemetry pipeline health; and produce observability error records. A platform conforms if it emits telemetry for major lifecycle activities; correlates telemetry across subsystems; distinguishes telemetry from audit and traceability records; provides execution, task, agent, model, tool, artifact, governance, traceability, state, and performance telemetry; supports monitoring and alerting; protects sensitive telemetry; supports retention and export governance; aligns with OpenTelemetry where claimed; and uses telemetry to support operational transparency and continuous improvement.

### 25.3 Deployment Conformance

A deployment profile conforms if it declares profile type and enabled subsystems, identifies control-plane and data-plane locations, identifies state, artifact, governance, traceability, and telemetry profiles, identifies isolation mode and recovery tier, records profile metadata, and passes deployment validation for the claimed profile. An enterprise deployment conforms if it provides durable state and controlled artifact repository storage, integrates identity and access control, enforces governance controls, preserves audit, traceability, and evidence records, supports runtime worker management, telemetry and alerting, backup and recovery, secret protection, validated and versioned configuration, and preserves required records for compliance.

A distributed deployment conforms if it provides durable queues, worker registration and heartbeat, leases and locks, distributed state consistency, project workspace isolation, worker-failure detection, split-brain detection, node-failure recovery, and governance and traceability consistency. A multi-tenant deployment conforms if it isolates tenant specifications, artifacts, state, governance records, traceability graphs, model context packages, and telemetry access, and scopes secrets by tenant, preventing cross-tenant access unless explicitly governed. A regulated deployment conforms if it enforces strong identity and access controls, separation of duties, integrity-protected audit records, restricted model and tool profiles, evidence retention, and disaster recovery testing, and blocks workloads when required compliance controls are missing.

A platform conforms if it supports at least one declared deployment profile; preserves logical platform architecture across profiles; supports local-first deployment where configured; supports independent scaling of scaling units where claimed; supports project isolation in shared deployments; supports governance consistency across environments; supports deployment validation; supports deployment telemetry and operational monitoring; supports backup, restore, and recovery appropriate to the declared profile; and prevents deployment profile claims that have not passed validation.
